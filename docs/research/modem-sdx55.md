# The OnePlus 8 Pro's modem: an external Snapdragon X55 on PCIe 2

Why this page: cellular (T06) was thought to be "start the SoC's MSS". It is not. Facts below are tagged **observed** (phone, RAM run, kernel `instantnoodle_modem.c`), **source** (the phone's own device tree and Android kernel log in `op8pro-data/`, the downstream kernel's `gcc-kona.c`, `pinctrl-kona.c`) or **inferred**.

## Topology
- **source:** the SM8250 has no modem of its own. The live device tree has `qcom,mdm0` (`compatible = "qcom,ext-sdx55m"`, esoc) and `qcom,pcie@1c10000` (PCIe 2) with a child `qcom,mhi@0` named `esoc0`. There is no `qcom,mss@4080000` node. CommCenter's "baseband" would be this chip.
- **observed (2026-10-28):** PCIe 2 up with the modem behind it: device `17cb:0306` (Qualcomm SDX55), class 0xff0000, link **5 GT/s x2 in 15 ms** after PERST is released, BAR 0 64-bit 4 KB at 0x64300000. MHI registers: MHIREGLEN 0x100, MHIVER 0xdeadbeef (not yet initialised: the boot ROM), MHICFG 0x800080, CHDBOFF 0x300, ERDBOFF 0x700, BHIOFF 0x100, BHIEOFF 0; BHI: EXECENV 0 (= PBL, the boot ROM: Linux/downstream numbering PBL 0, SBL 1, AMSS 2, RDDM 3, WFW 4, PTHRU 5, EDL 6), STATUS 0.
- **observed:** before the bring-up all control lines read low and are inputs: MDM2AP error (gpio 1) and status (gpio 3), AP2MDM status (gpio 56), error (57); PCIe 2's PERST gpio85, CLKREQ gpio86 (function 1 = pci_e2), WAKE gpio87. All in the TLMM **south** tile. PCIe 2's GDSC (GCC 0x106004) is collapsed and its clocks off at boot.
- **observed:** nothing else needs powering: with AP2MDM status high and error low, PERST released after the PHY is ready, the modem's boot ROM answers (Android's log shows the same: link 16 ms after "Release the reset").

## PCIe 2 recipe (differences from PCIe 0, the Wi-Fi's)
GCC offsets (gcc-kona.c; absolute = 0x100000 +): BCR 0x6000, GDSCR 0x6004, slv_q2a 0x6010, slv_axi 0x6014, mstr_axi 0x601c, cfg_ahb 0x6024, aux 0x6028, pipe 0x602c, aux RCG 0x6038, PHY BCR 0x1f01c; vote register **0x52010** (bits 10..15: slv_q2a, slv_axi, mstr_axi, cfg_ahb, aux, pipe). The PHY's reference is **gcc_pcie2_phy_refgen_clk (0x6f034)**, not PCIe 0's (0x6f02c), and the "ldo" clock of the device tree is **gcc_pcie_mdm_clkref_en (0x8c00c)**: with PCIe 0's reference clock the PHY never became ready (status 0x61). PARF 0x1c10000, PHY 0x1c16000 (status 0xa14 bit 6, power down 0xa40, 136-entry sequence from the device tree), DBI 0x64000000, iATU 0x64001000, config window 0x64100000, memory window 0x64300000 + 0x3d00000; SMMU streams 0x1d00 (bridge) and 0x1d01 (modem).

## What boots the modem (source: Android's log, `kmsg.txt`)
"esoc0" asked for by the radio layer -> PCIe 2 enabled -> link -> device 0002:01:00.0, BAR 0 4 KB -> `sdx55m/sbl1.mbn` through the MHI boot interface (BHI) -> ~2.6 s later PCIe 2 is taken down and up again (the modem has run its Sahara conversation and restarted) -> `rmnet_mhi0`, SSCTL. Firmware: modem partition (FAT) `image/sdx55m/`: sbl1.mbn 548 KB, tz, hyp, aop, apps, devcfg, apdp, sec.elf, xbl_cfg.elf, multi_image*.mbn, acdb, qdsp6sw.mbn **84 MB**, mdmddr.mbn, efs1-3.bin, modemr.jsn.
MHI channels of the device tree (`mhi,ee` is a mask of 1 << EE: 0x2 = SBL, 0x4 = AMSS): SAHARA 2 (UL) / 3 (DL) and BL 37 in SBL; in mission mode LOOPBACK 0/1, DIAG 4/5, QDSS 8/9, EFS 16/17, QMI0 20/21, QMI1 22/23, IP_CTRL 24/25, IPCR 32/33 (QRTR), TF 34/35, DCI 38/39, DUN 50/51, hardware IP channels 256/257 (IP_HW0, through the AP's IPA), RMNET_CTL 265/272; event rings 0..16 (ring 0 control, msi 1).

## What was achieved on the phone, in order (RAM runs, 2026-10-28, `instantnoodle_modem.c` + `hk_mhi.c`; boot-args in BOOT_ARGS.md)
All **observed**; each step is behind `modem=N`, nothing is flashed.
1. `modem=1` reads the control lines and PCIe 2's clocks (all off, all low). `modem=2`: PCIe 2 up (the device-tree's RC2 clocks, see above), 17cb:0306 at 5 GT/s x2 after 15 ms.
2. The modem's stream **0x1d01** of the apps SMMU sent through a context of ours (match register 5, context 4: the hypervisor takes it, as for the Wi-Fi and UFS). Proof that the modem's DMA goes through it: a first BHI attempt at an unmapped address gave a translation fault at that address in our context (fsr 0x80000402) and a different boot-ROM error code (0xef120700).
3. Firmware read from the phone's own **modem_b** (LUN 4, FAT16, 4096-byte sectors, 16 KB clusters; read only through the UFS backend, which now also reads LUN 4). modem_a holds another build of the same set; both are accepted by the boot ROM as far as tried (modem_a only to the BHI step).
4. **BHI**: the boot ROM takes the whole 547,904-byte `sbl1.mbn` (its signature segment is at 0x84000: a truncated image is refused with 0xef0e0002, the whole one first with **0xef0e0003** and then accepted). What made the difference between 0xef0e0003 and success (BHI_STATUS 0x81234567, EXECENV SBL, MHISTATUS 0x201) was changing two things at once: **enabling MSI in the device's capability** (address = a mapped page of the GIC's SETSPI register, data 960, all 32 vectors) and mapping the buffers **cacheable, inner shareable** (MAIR index 1) instead of non-cacheable. Which of the two it is was not separated (the boot ROM probably raises its completion interrupt and fails the transfer when it cannot).
5. **MHI host** (`hk_mhi.c`, a copy of the Wi-Fi's `mhi_host.c` with `no_bhie`): BHI (66 ms), READY, M0, and the SBL's **Sahara channels 2 (UL) and 3 (DL)** started, 486 ms after the start.
6. **Sahara** (version 2, 1024-byte command packets), HELLO_RESP must be **0x30 bytes** (with 0x20 the device answers END_IMAGE_TX status 5). Image ids -> files, as the modem asked for them: 37 multi_image.mbn, 34 mdmddr.mbn, (command-mode HELLO, answered with CMD_SWITCH_MODE 0), 40 apdp.mbn, 36 multi_image_qti.mbn, 41 devcfg.mbn, 25 tz.mbn, 33 hyp.mbn, 42 sec.elf, 23 aop.mbn, 16/17/20 efs1-3.bin (512 bytes each: the modem reads 40), 29 acdb.mbn, 8 qdsp6sw.mbn (84 MB), 6 apps.mbn. Five of these (40, 42, 29, 6 and the order) were guessed from Linux's table for the QDU100 plus "the next file not yet used": every END_IMAGE_TX had status 0, so the guesses are right. DONE answered with "image transfer complete" after 15 images and 88,080,147 bytes, in about 30 s.
7. Then **EE 2 (AMSS), MDM2AP status gpio 1, MHI event "mission"** with no link reset. The channels of the mission start (command completions): IPCR 32/33 and QMI0 20/21.
8. On QMI0's receive channel (21) the modem sends, as soon as it starts, a **QRTR version-2 HELLO** (36 bytes: 03 02 00 00 | size 20 | node 2 port 0xfffe -> 0xffff 0xfffe | cmd 2, 0x1ee3, 0xa). Not QMUX: CTL get version info on 20 gets no answer. IPCR 33 stays silent.

## Second round (2026-10-28, later): the router answers, and the modem resets itself 2.57 s after the mission's channels start
All **observed** unless said otherwise (kernel `instantnoodle_modem.c`, `modem=5`).
- **Start every software channel of the device tree**, not just IPCR/QMI0: DIAG 4/5, QDSS 8/9, EFS 16/17, QMI0 20/21, QMI1 22/23, IP_CTRL 24/25, IPCR 32/33, TF 34/35, DCI 38/39, DUN 50/51 and LOOPBACK 0/1 (event rings 1..3). Only then the modem's routers speak. **LOOPBACK works**: the modem echoes a send on channel 0 on channel 1, so the host-to-modem data path is sound.
- **Two QRTR links, one per modem node**: node 2 on QMI0 **20 (to the modem) / 21**, **version 2** headers (16 bytes, 16-bit nodes and ports); node 3 on DUN **50 / 51**, **version 1** headers (32 bytes). Each sends a HELLO (type 2, control port, payload `02 00 00 00 | e3 1e 00 00 | 0a 00 00 00` = cmd, then 0x1ee3 and 0xa) to the broadcast node within 20 ms of the channels starting; the reply goes on the same link with the same header version. IPCR 32/33, which the device tree names for QRTR (`mhi_qrtr`, `qcom,net-id` 3), stays silent. Each node's HELLO must be answered on its own link (answering node 3 only on node 2's link got nothing).
- **The modem then announces 16 to 48 services** (NEW_SERVER, via node 2's link; the count depends on timing): node 3 has DMS (2, port 59), NAS (3, 42), WMS (5, 58), UIM (11, 45), WDS (1, 47), VOICE (9, 41), CAT (10), PBM and others up to 0xe5; node 2 has 0x1771, 0x2b (SSCTL, instance 16, port 64), 0x31, 0x138b...
- **No QMI request gets a reply** (DMS get operating mode, tried over every link and header version, 600 ms each; UIM, NAS, WMS), neither in the window before the reset below.
- **The modem resets itself exactly 2.57 s (2575 ms, every run) after the mission's channels are started**: link down (reads all ones), MDM2AP status low, MDM2AP error fatal never asserted, and afterwards the boot ROM again (EE 0: a full restart, the images are lost). It does **not** happen when the channels are not started (20 s watched, EE 2 stable) nor does it depend on what we say (a "quiet" run that only starts the channels does the same), nor on M2 (the device held awake). Android's log has the same constant: PCIe 2 disabled and enabled 2.576 s after sbl1.mbn was loaded.
- **Hypothesis (inferred):** the modem's AMSS wants the host to reset the link (PERST about 15 ms, Android's "msm_pcie_disable"/"msm_pcie_enable") inside that window, and resets itself if not. Cycling the link at the moment MDM2AP status is high and EE is 2 does **not** retrain: the link stalls in LTSSM 5 (Configuration.Linkwidth) with a soft PERST cycle (also with the port logic told two lanes) and in LTSSM 3 with a full controller power cycle. Earlier first tries: PERST held 130 ms restarts the modem in its boot ROM; a cycle during SBL does not train.
- Android's `esoc-mdm-4x.c` / `esoc-mdm-pon.c` (read from the OnePlus 8 Lineage kernel on GitHub): SDX55M power-on is a **PMIC warm reset of the modem** (`qpnp_pon_modem_pwr_off(PON_POWER_OFF_WARM_RESET)`), 150 ms, then AP2MDM_STATUS high, then it waits for MDM2AP_PBLRDY (a pin we have not seen) and requests the image; AP2MDM_ERRFATAL is driven low; MDM2AP status low while "ready" is treated as an unexpected reset. The AP2MDM_STATUS line is otherwise untouched by the host. `qcom,net-id` of the qrtr node and the MHI `mhi_qrtr` mapping are in the device tree (above).

## The redwood work (POCO X5 Pro, internal MSS): what carries over
The synced repository `hackios-xnu-kernel` (`docs/cellular.md`, `docs/ru/cellular.md`, `xnu/files/bsd/dev/hakios.{mpss,qmi,ipa}.c`) got the other kind of modem (an on-chip Hexagon MPSS over GLINK/QRTR) as far as registration and a data session: QMI clients (DMS, UIM Get Card Status 0x2f, **UIM Switch Slot 0x46**, **UIM Change Provisioning Session 0x38** to bind the USIM as the primary GW application, NAS Get System Info 0x4d / Initiate Network Register 0x22 / signal strength, WDS with **DPM Open Port + WDA Set Data Format + Bind Mux Data Port** before Start Network Interface), a hook of SpringBoard's `_updateSignalStrengthItem:withData:SIMInfo:barsGetter:barsSetter:` for the signal bars (`inject_sb.c`), and the data path as an Ethernet-looking `en1` with a faked router and DHCP. Its lessons for the modem's behaviour: the modem stays OFFLINE ("not ready", error 52) until the application processor serves **pd-mapper (QMI 64, v257)** and **tqftpserv (QMI 4096)** and, for the internal modem, **rmtfs (QMI 14)**; it then goes online by itself and **crashes a few seconds later in `enl2_dl` unless the IPA data path exists**. For this external modem the data plane is the AP's IPA over MHI hardware channels (256/257 in the device tree), which is not started here: a candidate cause of the 2.57 s reset once the link problem is solved.

## Correction (2026-10-28, late): the 2.57 s reset was a wrong channel table; QMI works on the first link

The device tree names the MHI channels by their **decimal** channel number (node `mhi_chan@20` is channel 20, as its `reg` property says); the sections above read them as hex and started the wrong channels (QMI0 20/21 was right by luck of the first test; the rest, e.g. "DUN 50/51", were other channels). With the real table (LOOPBACK 0/1, DIAG 4/5, QDSS 8/9, EFS 10/11, QMI0 14/15, QMI1 16/17, IP_CTRL 18/19, **IPCR 20/21**, TF 22/23, DCI 26/27, DUN 32/33, IP_HW0 100/101) the modem **does not reset** (observed, run m54: `modem_quiet=3 modem_chans=129` = LOOPBACK + IPCR only, plain first-link mission, 60+ s stable, EE 2, MHISTATUS 0x201). Consequently these conclusions above are **wrong / not needed**: "resets itself 2.575 s after the channels start", "the host must reset the link in time", "the IPA must be handshaken first", the link-cycle experiments (not needed on the first link; the Android sequence stays documented). Observed on the stable link: QRTR v2 HELLO answered, DMS/NAS/UIM/WMS/WDS/VOICE announced by node 3, DMS operating mode answers (3 = offline), NAS serving system and signal strength answer, UIM Get Card Status result 0, WMS gets error 52 (not ready) while the radio is offline.

## What made it work (2026-10-29; all observed on the phone unless marked)

1. **RESUME_TX must be a 20-byte control message** (cmd 7, our node, our port, two zero words). The modem's AMSS router logs "control message too short" and ignores a 12-byte one; its sender then blocks after 10 datagrams to a destination (QRTR's flow limit) and every QMI reply and TFTP request stops (the "stall at ~13 s, 59 datagrams" of the earlier runs; the modem's own sends fail with errno 16 after 1 s). Both of the old explanations (modem resets itself; IPA handshake needed) were wrong.
2. **DIAG works as a window into the modem**: start channels 4/5 (bit 1 of `modem_chans`), send HDLC `7d 05 00 00 ff ff ff ff` (set all message masks); extended message packets (0x79) carry the format string and file name, e.g. `tftp_client.c`, `mcfg_remote.c`, `sfs_*`. This is how the TFTP lookup (`name = [sid = 4096, iid = 3]`, "could not resolve remote host") and the MCFG walk were found. (observed)
3. **TFTP service** (the modem's MPSS and its application processor read their carrier configs from the AP and keep their EFS there): announce NEW_SERVER {4096, instance word, node 1, port 0x4002} to **both node 2 and node 3**, instance words 0..5 raw and 1|i<<8 (the client's name is the raw word 3). RFC 1350 + options: `blksize` (we offer 1024), `tsize` (STAT = RRQ with tsize=0; the client ends with ERROR 9 "End of Transfer", which is normal), `timeoutms`, `seek`/`rsize` (partial reads), `wsize` (**must be answered, wsize=1**, or the client waits for a window of ten blocks and re-acknowledges forever). Paths `/readonly/firmware/image/...` are the FAT of `modem_b` (`image/...`); `/readwrite/...` is its EFS scratch (writes are accepted and discarded here). (observed)
4. **EFS images**: the modem boots with whatever Sahara serves for ids 16/17/20; the firmware partition has 512-byte stubs, so it starts with an empty EFS and spends many minutes loading every carrier config (`mcfg_remote`) before DMS leaves "not ready" (QMI error 52). The phone's Android keeps its real EFS in the partitions `mdm1m9kefs1/2/3` (**LUN 5**, 2 MB each, header "IMGEFS1/2"; image id = the first word: 16, 17; efs3 is empty): serving those (read only) makes the modem ready in seconds. The modem's EFS sync (Sahara memory debug on MHI channels 10/11, which `ks` answers on Android) is answered and its bytes thrown away. (observed)
5. **QMI details**: UIM Get Card Status TLV 0x10 (slot header 6 bytes, application 7 + AID + 7 bytes); PIN1 verify is UIM 0x26 with TLV 1 {session 0, aid length 0} and TLV 2 {pin id 1, length 4, "0000"} (answered result 0; application state 2 -> 7); DMS Set Operating Mode online is 0x2e TLV 1 {0}; NAS serving system 0x24 shows registration 1, CS 1, PS 1, radio interface 8 (LTE); WMS Raw Send 0x20 with TLV 1 {format 6, length, PDU with an empty SMSC byte} answered success with a message id. Only an observation by the recipient proves the SMS arrived.
6. Untested/unknown: voice, data (MHI hardware channels 100/101, IPA), receiving SMS, a modem EFS that persists, the iOS side.
